## 1. React Error #185 — Nurse Portal Crash

### Problem
The nurse portal crashes in production with React minified error #185. This error means a JavaScript object is being passed directly as a React child — e.g. `{someObject}` where JSX expects a string, number, or element.

### Root Cause
The nurse dashboard itself maps correctly over vitals data (keys present, optional chaining used). The likely source is in one of the sub-components rendered inside `PatientCareView` when an API returns data in an unexpected shape — particularly `PrescriptionView` or `ProceduresView` when a field expected to be a string is instead an object (e.g. a nested medication object rendered directly).

### Fix Design

**Step 1 — Add ErrorBoundary**  
Wrap `<NurseDashboard />` in an `ErrorBoundary` component (class component) that catches render errors and displays a readable message instead of a blank crash. This is a safety net, not the root fix.

**Step 2 — Trace and fix the bad render**  
Run in development mode and inspect the component stack. Add null guards and explicit field access to every `.map()` call in:
- `components/nursing/prescription-view.tsx`
- `components/nursing/procedures-view.tsx`
- `components/nursing/patient-care-view.tsx`

Pattern to apply:
```tsx
// Before (dangerous)
{prescription.medication}  // could be an object

// After (safe)
{typeof prescription.medication === 'string'
  ? prescription.medication
  : prescription.medication?.name ?? '—'}
```

**Step 3 — Add empty-state guards**  
Every list render must handle the empty/undefined case:
```tsx
if (!prescriptions || prescriptions.length === 0) return <EmptyState message="No prescriptions" />;
```

### Files Changed
- `components/nursing/prescription-view.tsx`
- `components/nursing/procedures-view.tsx`
- `components/nursing/patient-care-view.tsx`
- `components/error-boundary.tsx` (new, or reuse existing `error-boundary.tsx`)
- `app/nurse/page.tsx` (wrap dashboard with ErrorBoundary)

## 2. Auth & Role-Based Access Control

### Problem
The login form presents a role selector dropdown. Users can attempt to log into portals they don't belong to. Although the backend already validates and rejects mismatched roles, the UX is confusing and the error message references "role selection" — which should not exist.

### Fix Design

**Remove the role selector entirely from the login form.**

The `login()` function in `components/login-form.tsx` will no longer send a `role` parameter. The backend `/api/auth/login` already returns the user's actual role in the JWT and response body. The frontend uses that role to redirect:

```ts
switch (user.role) {
  case "Nurse":         router.push("/nurse");        break;
  case "Clinician":     router.push("/clinician");    break;
  case "Receptionist":  router.push("/receptionist"); break;
  case "Hospital Admin":router.push("/admin");        break;
  case "Cashier":       router.push("/cashier");      break;
  case "Pharmacist":    router.push("/pharmacist");   break;
  case "Lab Tech":      router.push("/lab-tech");     break;
  case "Radiologist":   router.push("/radiologist");  break;
  case "Dentist":       router.push("/dentist");      break;
  case "Midwife":       router.push("/midwife");      break;
  default:              router.push("/dashboard");    break;
}
```

The success redirect currently goes to `/dashboard` for everyone. This is replaced with role-based routing. `/dashboard` remains as a fallback for unknown roles.

**Update login error message:** Remove any reference to "check your role selection". Generic message: "Invalid credentials. Please check your email and password."

**Backend cleanup:** The `role` field in `LoginSchema` is already `.optional()`. No backend change needed — it simply won't receive a role from the form anymore. The existing role-mismatch guard code can be removed since it's now unreachable.

### Files Changed
- `components/login-form.tsx`
- `app/api/auth/login/route.ts` (minor: remove unreachable role-mismatch branch)

## 3. Patient After-Visit Summary & Discharge Export

### Overview
This is the core document a patient leaves with. It is generated by the clinician at the end of a consultation (OPD) or at discharge (inpatient). The clinician finalizes and shares it; the admin receives a print notification and gives the physical copy to the patient.

Two document types, one unified workflow:
- **After-Visit Summary (AVS)** — OPD / outpatient consultation
- **Discharge Summary** — inpatient admission

Both are generated as PDFs using the existing PDFKit infrastructure at `/api/exports/patient-discharge/route.ts`.

### Document Layout (matches paper form)

```
┌─────────────────────────────────────────┐
│  [Logo]  Dayspring Medical Centre        │
│          Address | Phone | Email         │
│          Clinic Hours                    │
│                                          │
│          After-Visit Summary / Discharge │
│          Summary                         │
├─────────────────────────────────────────┤
│ OPD No:         | Patient Name:         │
│ Sex:            | Age:                  │
│ Visit Date:     | BP:  (if recorded)    │
├─────────────────────────────────────────┤
│ Chief Complaint:                         │
│ (free text from consultation)            │
│                                          │
│ PmHx: (past medical history)            │
│ O/E:  (on examination findings)         │
│ Impression: (diagnosis)                 │
├─────────────────────────────────────────┤
│ Investigations:                          │
│  Lab:      [test] — [result/pending]    │
│  Radiology: [test] — [result/pending]  │
├─────────────────────────────────────────┤
│ Treatment Given:              QTY        │
│  [drug name, route]   [dose × duration] │
│  ...                                    │
├─────────────────────────────────────────┤
│ Nursing Notes: (if any)                 │
├─────────────────────────────────────────┤
│ Billing Summary:                         │
│  [item]              [amount]           │
│  Total:              [total]            │
├─────────────────────────────────────────┤
│ Review TCA: [date]                      │
│ Discharge Instructions: [text]          │
├─────────────────────────────────────────┤
│ Doctor's Name: ___________              │
│ Sign: ___________        Date: ___      │
│                                         │
│       "Together with the Healer"        │
└─────────────────────────────────────────┘
```

**Only include sections where data exists.** If no labs were ordered, the Investigations section is omitted. If no nursing notes exist, that section is omitted. The document adapts to what was actually done.

### Data Fetched Per Visit
The export endpoint fetches for the specific `patientId` + `visitId` (OPD encounter ID or admission ID):

| Data | Source Table |
|------|-------------|
| Patient demographics | `patients` |
| Visit date, OPD No | `opd_encounters` or `admissions` |
| Chief complaint, PmHx, O/E, Impression | `consultations` |
| Latest BP at visit | `vital_signs` |
| Lab orders + results | `lab_tests`, `lab_results` |
| Radiology orders | `radiology_orders` (if table exists) |
| Prescriptions (drug, dose, freq, route, duration) | `prescriptions` |
| Nursing notes | `nursing_notes` |
| Billing items + total | `billing_items`, `invoices` |
| Discharge instructions | `consultations.discharge_instructions` or `admissions` |
| Clinician name | `users` (via consultation) |

### Generate & Share Workflow

**Step 1 — Clinician generates**  
A "Generate Summary" button appears in the clinician's `PatientConsultation` component, in the header next to the existing Print button. Clicking it calls `POST /api/exports/patient-summary` with `{ patientId, visitId, type: "avs" | "discharge" }`.

**Step 2 — Server generates PDF**  
The API endpoint fetches all visit-specific data, renders the PDFKit document, stores the PDF as a file (or base64 blob) in the DB table `patient_summaries` with:
- `patient_id`, `visit_id`, `generated_by` (clinician user ID), `generated_at`, `status: "pending_print"`, `pdf_data`

**Step 3 — Admin notification**  
After saving, the endpoint calls the existing notification infrastructure to notify users with role `Hospital Admin`: *"Patient summary ready for printing: [Patient Name] — [Visit Date]"* with a link to `/admin/print-queue`.

**Step 4 — Admin prints**  
The admin portal has a "Print Queue" page listing all `pending_print` summaries. Admin clicks a summary → opens PDF in browser → prints. On print/download, status updates to `"printed"` and a second audit log entry is written.

**Step 5 — Finalization lock**  
Once status is `"printed"`, the summary is locked. The clinician cannot regenerate it (the button becomes disabled for that visit). If a correction is needed, only a Hospital Admin can unlock it (sets status back to `"pending_print"` with an audit entry noting who unlocked and why).

### Audit Trail
Every state transition is recorded in the existing `audit_logs` table:
- `SUMMARY_GENERATED` — clinician ID, patient ID, visit ID, timestamp
- `SUMMARY_PRINTED` — admin ID, timestamp
- `SUMMARY_UNLOCKED` — admin ID, reason, timestamp

### New DB Table: `patient_summaries`
```sql
CREATE TABLE patient_summaries (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  patient_id UUID NOT NULL REFERENCES patients(id),
  visit_id UUID NOT NULL, -- references opd_encounters.id for AVS, admissions.id for discharge
  visit_type TEXT NOT NULL CHECK (visit_type IN ('avs', 'discharge')),
  generated_by UUID NOT NULL REFERENCES users(id),
  generated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  status TEXT NOT NULL DEFAULT 'pending_print'
    CHECK (status IN ('pending_print', 'printed', 'unlocked')),
  pdf_data BYTEA NOT NULL,
  unlocked_by UUID REFERENCES users(id),
  unlocked_at TIMESTAMPTZ,
  unlock_reason TEXT
);
```

### Files Changed / Created
- `app/api/exports/patient-summary/route.ts` (new — existing `/patient-discharge` route is kept for backwards compatibility; this is a new parallel route)
- `app/api/exports/patient-summary/[id]/route.ts` (new — GET for admin to fetch PDF)
- `app/admin/print-queue/page.tsx` (new — admin print queue UI)
- `components/doctor/patient-consultation.tsx` (add "Generate Summary" button)
- `migrations/20260414_patient_summaries.sql` (new table)

## 4. Nurse Portal — Prescription Visibility

### Problem
Nurses need to see all prescriptions ordered by clinicians for their patients. The existing `PrescriptionView` component exists but may not be surfaced prominently enough in the nurse workflow.

### Design
The `PatientCareView` already has tabs. Ensure the prescription tab:
1. Fetches all prescriptions for the patient from `GET /api/pharmacy?patientId=X` or a dedicated endpoint
2. Displays: drug name, dosage, frequency, route (oral/IV/injection), duration, ordering clinician, ordered date
3. Clearly distinguishes **active** prescriptions from **completed/discontinued** ones (color-coded badge)
4. Shows administration status from the MAR (see Section 5) inline — e.g. "3/6 doses given"

### Files Changed
- `components/nursing/prescription-view.tsx` (enhance data fetching and display)
- `app/api/prescriptions/route.ts` (verify endpoint supports nurse role access)

## 5. Nurse Portal — Medication Administration Record (MAR)

### Overview
The MAR tracks what was prescribed vs what was actually administered. The backend endpoint `POST /api/prescription-administrations` already exists. This section adds the full frontend UI.

### UI Design (within PatientCareView)

A new "MAR" tab in the nurse's patient care view shows a table:

```
┌──────────────┬──────────┬───────────┬──────────────┬──────────────┬────────────┐
│ Medication   │ Due Time │ Given At  │ Given By     │ Dose Given   │ Status     │
├──────────────┼──────────┼───────────┼──────────────┼──────────────┼────────────┤
│ Amoxicillin  │ 08:00    │ 08:15     │ Nurse Amina  │ 500mg oral   │ ✅ Given   │
│ Paracetamol  │ 12:00    │ —         │ —            │ —            │ ⏰ Due     │
│ IV Tramadol  │ 06:00    │ —         │ —            │ —            │ ❌ Missed  │
└──────────────┴──────────┴───────────┴──────────────┴──────────────┴────────────┘
```

**Status logic:**
- `Given` — administration record exists for this dose
- `Due` — scheduled time is in the future (within 1 hour window)
- `Missed` — scheduled time has passed with no administration record
- `Delayed` — scheduled time has passed but within a grace period (configurable, default 30 min)

**Recording administration:**
Nurse clicks "Give" on a due/missed row → a small form appears inline:
- Dose given (pre-filled from prescription)
- Route (pre-filled, editable)
- Notes (optional)
- Confirm button

On confirm, calls `POST /api/prescription-administrations` and updates the row status immediately.

**Due-time calculation:**
Prescriptions have a frequency (e.g. "OD" = once daily, "BD" = twice daily, "TDS" = three times daily, "QID" = four times daily, "stat" = one-off immediate). The system calculates expected administration times based on frequency and prescription start time. "stat" doses have no schedule — they show as "Due immediately" until given.

> **Implementation dependency:** Verify that the `prescriptions` table has a `start_date`/`start_time` column. If not, the MAR will use `created_at` as the prescription start time for scheduling calculations.

### Files Changed / Created
- `components/nursing/mar-view.tsx` (new component)
- `components/nursing/patient-care-view.tsx` (add MAR tab)
- `app/api/prescription-administrations/route.ts` (verify GET endpoint exists for listing)
- `app/api/prescription-administrations/[id]/route.ts` (if needed for GET by prescription)
- `lib/mar-utils.ts` (new — frequency parsing, due-time calculation)

## 6. Terminology — "STAT" → "Very Urgent" (triage priority only)

### Scope clarification
"stat" as a **clinical dosing term** (meaning "give immediately, one-off dose") must **not** be changed. This is standard medical Latin and appears on the paper form.

Only the **triage priority category label** "STAT" should be changed to "Very Urgent". The codebase grep confirmed no remaining "STAT" strings in .ts/.tsx files — the terminology is already updated in code. Remaining work:
- Check SQL migrations and seed data for any `'STAT'` enum value
- Check any report templates or PDF label strings inside the export endpoint
- Verify the triage input form uses "Very Urgent" as a selectable option

### Files to Check
- `dayspring.sql` (seed data)
- `migrations/` directory (any enum definitions)
- `app/api/exports/patient-discharge/route.ts` (label strings)

## Architecture Summary

```
Clinician Portal
  └─ PatientConsultation
       └─ "Generate Summary" button
            └─ POST /api/exports/patient-summary
                 ├─ Fetches: consultation, prescriptions, labs, vitals, billing, nursing notes
                 ├─ Renders: PDFKit document (paper form layout)
                 ├─ Stores: patient_summaries table
                 └─ Notifies: Hospital Admin

Admin Portal
  └─ /admin/print-queue
       └─ Lists pending summaries
            └─ Click → view PDF → print → status: "printed"

Nurse Portal
  └─ PatientCareView
       ├─ Prescription tab (enhanced)
       └─ MAR tab (new)
            └─ POST /api/prescription-administrations (existing)

Login Form
  └─ No role selector
       └─ POST /api/auth/login → returns role → client redirects
```
